# Agent retrieval benchmark

An empirical comparison of three retrieval architectures over a **manually
adjudicated** 30-question evaluation set. The dataset and harness are
committed; the report is generated from the local build.

```bash
npm run benchmark
```

## The question set

`src/adjudicated.mjs` defines 30 questions across six categories. Every
ground-truth field (relevant documents, citations, required passages,
expected outcome) is computed from the compiled artifacts — catalog, graph,
claims, evidence, book record — and the queries were written and reviewed by
hand. Nothing is generated by an LLM and nothing is tuned to favour an
architecture.

| Category | Questions | What it tests |
|---|---|---|
| `direct-factual` | 7 | a property of one document (URL, title, ISBN, date) |
| `cross-document` | 7 | the answer spans several documents |
| `relationship-traversal` | 6 | a graph traversal (`implements`, `documents`, `prerequisite_for`) |
| `claim-verification` | 5 | a claim's existence, assessment and authoritativeness |
| `contradiction-detection` | 2 | the answer is that no contradiction exists |
| `insufficient-evidence` | 3 | the corpus does not contain the answer |

Each question carries an `expectedOutcome` of `supported` or `no_support`. A
`no_support` question must not be answered by any document; an architecture
that returns a confident-looking document for it is producing an unsupported
claim. That is measured directly as the **false-support rate**.

## The three architectures

| | A · Conventional crawling | B · Catalog + graph | C · Catalog + graph + Markdown |
|---|---|---|---|
| Discovery | Crawl every HTML page into a local full-text index | Fetch `/agents/catalog.json` + `/agents/graph.json` once | Same as B |
| Ranking | Term overlap over raw HTML text | Term weighting over catalog metadata; the graph for relationship questions | Same as B |
| Body fetch | None after the crawl | Fetch the top 5 HTML pages | Fetch the top 5 Markdown mirrors |
| Structured claims | None | claims.json for claim questions | Same as B |

### Cache assumptions (stated explicitly)

- **A** crawls the whole site once per session and keeps a local index. It has
  no catalog and no graph.
- **B/C** fetch `catalog.json` + `graph.json` once per session and cache them.
  Document bodies are fetched per query and not cached.
- These are per-session assumptions. A real deployment may cache more; the
  benchmark does not model a CDN or a shared cache.

## Results (30 questions, 197 articles)

| Metric | A · Crawling | B · Catalog + graph | C · + Markdown |
|---|---|---|---|
| Recall@5 | 0.313 | **1.000** | **1.000** |
| Precision@5 | 0.083 | 0.671 | 0.671 |
| Citation accuracy | 0.417 | **1.000** | **1.000** |
| Passage recall | **0.810** | 0.286 | 0.571 |
| False-support rate | 1.000 | **0.333** | 0.500 |
| One-time bytes | 30,808 KB | **265 KB** | **265 KB** |
| Total bytes | 30,808 KB | 10,405 KB | **1,826 KB** |
| Requests / query | 0.0 (after crawl) | 2.6 | 2.6 |
| Latency / query (local) | 9.7 ms | 0.2 ms | 0.2 ms |

## What the experiment establishes

1. **The compiled catalog retrieves the right documents.** Recall@5 rises
   from 0.313 to 1.000 and citation accuracy from 0.417 to 1.000. The graph
   answers the relationship questions directly; a crawler has no graph.
2. **The one-time cost drops by two orders of magnitude.** Crawling every page
   costs 30.8 MB; the catalog and graph cost 265 KB.
3. **Canonical Markdown is the cheapest body transport.** For the same
   ranking, Markdown mirrors cost 1.8 MB across the benchmark against 10.4 MB
   for the HTML pages — a 5.7× reduction on top of the catalog saving.
4. **Metadata alone does not carry the answer.** B's passage recall is 0.286:
   it retrieves the right documents, but a title, description and tag list do
   not contain a `doc_id` or a publication date. C raises passage recall to
   0.571 by fetching the Markdown bodies, which carry the frontmatter. This is
   the honest trade-off the benchmark exists to surface.
5. **A crawler produces more unsupported answers.** A's false-support rate is
   1.000: for every question the corpus cannot answer, it still returns a
   document. B and C return nothing for claim questions, which lowers their
   false-support rate to 0.333 and 0.500.

## What it does not establish

- **LLM reasoning.** The benchmark measures whether the right document is
  retrieved, not whether an agent's answer is correct. It does not show that
  the architecture improves reasoning, only that it improves retrieval and
  reduces unsupported answers.
- **Network latency.** The benchmark runs against the local build. Latency
  figures are local processing time; bytes transferred are the artifact sizes
  a real client would download, which is the dominant term on a network.
- **A production crawler.** Architecture A uses naive HTML text extraction
  (chrome stripped, RSC payload left mangled). A crawler with better
  extraction and a real inverted index would improve recall and passage
  recall, but would still pay the full crawl cost and would still lack the
  typed graph and the claim model.
- **Generalization.** One site, one corpus, one point in time. The absolute
  numbers will differ elsewhere; the direction — a compact catalog plus typed
  metadata retrieves at least as well as crawling and costs far less — is the
  claim.
- **The adjudicated set is small.** Thirty questions is enough to expose the
  architectural differences, not to estimate population-level retrieval
  quality. The per-category counts are in the report.

## Reproducing

```bash
npm run build
npm run benchmark
```

The harness reads `.next/server/app`, writes
`data/adjudicated-questions.json` and `data/benchmark-report.json`, and prints
the table above. The dataset is deterministic: the same build produces the
same questions and the same numbers.

## Agent experiment (LLM question answering)

`src/agent-experiment.mjs` is the second experiment category. It feeds the
retrieved documents to a real model and measures what the model then says.

```bash
npm run benchmark:agent
```

Architectures A/B/C use the same retrieval as the deterministic benchmark; D
is a parametric control with no retrieval. B and C receive the compiled catalog
metadata, the **full typed graph** and the **claim index**; C adds the Markdown
bodies. Every architecture gets the same per-document context budget, so the
comparison is about representation, not about how much text each side may read.

Measured per question:

| Metric | What it means |
|---|---|
| `ruleCorrectRate` | A transparent, category-aware rule check. Reported as rule-based, not as human adjudication. |
| `citationAccuracy` | The answer contains an expected canonical URL. |
| `abstentionRateOnNoSupport` | The model said the corpus does not contain the answer. |
| `unsupportedClaimRate` | A `no_support` question answered anyway, or an answer with a fabricated citation. |
| `fabricatedCitationRate` | The answer contains a URL that resolves to nothing in the corpus. |
| `contradictoryRate` | The answer both abstains and cites. |
| `tokensPerQuery`, `latencyMsPerQuery` | Model cost and latency. |

The model is local (`lfm3-omni:latest` through Ollama), recorded in the report
along with the exact prompt, temperature and token budget. Cold and warm passes
are reported separately. Raw answers are committed in
`data/agent-experiment-report.json` for human review.

**Limitation:** only one model family was available on this machine. The
results do not establish that the architecture improves reasoning, only what
this model did with each representation.
