## 2. Verified findings

### F1 — Draft material is published (defect, confirmed in production)

`src/lib/posts.ts` reads every `.md` file in `content/research/` and never
inspects the `draft` frontmatter field. Two posts carry `draft: true`:

- `2026-07-22-if-the-loop-is-the-product`
- `2026-07-23-building-the-scientific-question-compiler`

Both are present in the production catalog and served as live pages. The
reference article states "drafts never reach the corpus"; that is not true of
the shipped code. This is the only finding that leaks unpublished material.

### F2 — The reference article documents an architecture the repo does not contain (documentation defect)

The November 12 article presents `lib/corpus/{schema,load,graph,emit}.ts`,
zod schemas, `content/articles/*.mdx`, `content/projects.json`,
`content/concepts.json`, `content/paths.json`, and `content/book/*.json`. None
of those paths exist. The shipped implementation is:

- `src/lib/agent-resources-core.ts` — pure builders for the six resources
- `src/lib/agent-resources.ts` — binds those builders to config/posts/taxonomy
- `src/lib/posts.ts`, `taxonomy.ts`, `chapters.ts`, `book-links.ts`,
  `relations-core.ts` — the registry and graph
- `content/research/*.md` — the article archive (markdown, not MDX)

The article's `llms.txt`, `catalog.json`, `index.json` and `book.json` shapes
are also aspirational: the shipped `index.json` carries no per-resource content
hash, and the shipped `book.json` has no `conduct` block or `not_provided`
list. The article is a design document, not a description of the code. That is
fine as an intent statement, but it must not be read as a build report.

### F3 — No Markdown mirrors (missing deliverable)

`/research/{slug}.md` returns 404 in production. The article lists this as
next step 1 ("Emit `/research/<slug>.md` at build time from the MDX source").
This is the first major deliverable of the present directive.

### F4 — No single-corpus conformance command and no deployment smoke test (missing deliverable)

The validators exist and are real (`validate:content`, `validate:build`,
`validate:agents`, `audit`, `check:routes`), but:

- there is no one command that validates the complete corpus end to end;
- nothing checks the *deployed* site against the locally generated artifacts
  (HTTP status, content type, caching, ETag, hashes);
- nothing verifies deterministic rebuilds or Markdown structure/hashes.

### F5 — `validate-agents.mjs` derives the article set from the directory, not from the loader

It builds `postSlugs` by listing `content/research/*.md`, so it cannot detect
F1 and will disagree with the catalog the moment drafts are filtered in
`posts.ts`. `audit-site.mjs` has the same pattern. Both must read the same
published-post source as the site.

### F6 — The graph is small and the claim/evidence model does not exist (missing deliverable)

Five relation types, 98 edges, all resolving. There is no claim schema, no
evidence schema, no epistemic assessment, and no distinction between declared
and proposed (AI-generated) relationships. `ABSENT_RELATIONS` is a
hard-coded list, not derived from a controlled vocabulary.

### F7 — No SDK, MCP adapter, or retrieval benchmark (missing deliverables)

None of the three exist in the repository.

## 3. Non-findings (checked and clear)

- **Production/repo drift:** none after the fast-forward. Local `main` was
  simply two commits behind `origin/main`; the November 12 article exists in
  git at `47c2a39`. Production's 199 articles match the archive exactly.
- **Graph integrity:** 98 edges, 0 dangling in production and in the repo.
- **Determinism:** `agent-resources-core.ts` is pure (no clock, no
  randomness, no filesystem, no `@/` imports); two builds of the same commit
  are byte-identical by construction and by test.
- **Book record:** no invented availability, rating or review; the price is
  labelled configured; `purchase.authorizedBy` is present.
- **Build gates:** `prenode` and `check-images` fail closed; CI runs the full
  gate on every push to `main`.

## 4. Implementation sequence

1. **Phase 1** — fix F1; implement F3 (Markdown mirrors) with hash/byte
   verification and tests; make the validators read the published-post source
   (F5); add artifact-integrity checks.
2. **Phase 2** — one conformance command over the whole corpus plus a
   deployment smoke test (F4); CI integration.
3. **Phase 3** — controlled graph vocabulary, claim/evidence schemas,
   declared-vs-proposed separation, provenance validation (F6).
4. **Phase 4** — TypeScript knowledge SDK and MCP adapter (F7).
5. **Phase 5** — retrieval benchmark with three architectures and an honest
   evaluation report (F7).
6. **Phase 6** — evaluate extracting the compiler into a reusable project.

Each phase ends with tests, a compiler run, artifact inspection, a diff review,
a documentation update and one descriptive commit. A phase is not claimed
complete unless its acceptance criteria pass.
